# Agentic decision architecture proposal

> **Status:** proposal from the agentisation review (2026-11-25); its decision is recorded in
> [the ADR](decisions/2026-11-25-governed-agent-research-boundary.md). Code it mentions that is not
> on `main` is on branch `research/agentic-decision-architecture`.

**Status:** Proposed. The implemented experiment is an offline synthetic route calculation and evidence-gated workflow.

## Dispatch and ownership

1. Call a pure function when typed inputs and a formula fully specify the answer. Use a domain service when the formula needs governed evidence, effective-date resolution, conversions or portfolio context.
2. Dispatch known multistep tasks through an explicit workflow. Apply an event trigger when domain facts change within a watched dependency and horizon.
3. Run the mathematical optimiser for a choice among coupled alternatives. It owns constraints, feasibility, tolerances, objective and candidate comparison.
4. Use a single LLM call for extraction or prose when the information is already scoped and the desired output is defined.
5. Trial a governed planner only when the next investigative step plausibly depends on earlier findings. Limit follow-ups and expose deterministic capabilities through the current registry. Use multiple roles only after measuring value beyond an independent deterministic challenger.

Fast path resolves the event, affected keys and first check. Optimisation path runs authorised scenario solves against versioned inputs, returning feasible incumbents with termination status and explicit gaps where supported. Agentic path operates asynchronously over selected results and may propose follow-ups or scenarios. Optional analysis can arrive after the first alert or decision pack. A deadline latches the last reproducible result and marks outstanding investigation.

## Portfolio and LNG boundary

Freeze an authorised portfolio snapshot and manifest at an as-of cutoff. Include book/mandate, contracts and amendments, confirmed cargo and terminal windows, rights, storage inventories, Send-out and pipeline profiles, credit/hedges and available prices. Cite snapshot and component versions. Resolve gas-day and unit conversions at the domain boundary. Partition projections by tenant, book or authorised cross-book scope. Keep the existing transactional model and `LiveSnapshotReader` pattern. Follow the separate LNG team's canonical types and delivery dates.

Evaluate affected cargoes together when they share a resource. The optimiser models capacity by resource and time interval, subtracts authoritative commitments, and returns analytical alternatives. Assumptions and hypothetical allocations live in the scenario. Concurrent analyses may share a snapshot, but cannot change live resource balances. Before approval or export, compare dependency versions against current state and request re-evaluation after a material change. Any future committed reservation would require versioned atomic allocation by the authorised system and separate product approval. Decision Cases hold reviewed packages and status references.

## Evidence and execution policy

| Evidence state | Required behavior |
| --- | --- |
| VERIFIED | Authorised source and version matched to proposition, scope, effective period and unit. Contractual rules need a reviewer and approved version. |
| CONDITIONAL | Preconditions are explicit and the result remains contingent. |
| INDICATIVE | Research estimates, synthetic cases and non-executable quotes. Carry the class into downstream outputs. |
| UNKNOWN | Withhold dependent claims and surface the missing input. |
| CONFLICTED | Preserve conflicting evidence and require reconciliation or authorised resolution. |

Keep physical feasibility, commercial feasibility and execution confirmation as separate axes. Use explicit conditional, awaiting confirmation, not assessed and infeasible outcomes. Physical capacity says little about ownership and access. Executable quotes, commercial rights and current credit and liquidity are separately necessary for a commercial assessment. The prototype reports synthetic scenario feasibility and commercial status `NOT_ASSESSED`.

Provider input is untrusted text or data. Resolve observations and extracted terms to typed candidate facts. Tool argument schemas, action allowlists and data scopes come from Nexus. Bind roles and row visibility to authenticated human or persisted service identities, check again at each invocation and before external model processing, and reject model-supplied authority or citation IDs. Where terms restrict external AI consumption, use an approved local path or deterministic fallback. Check references against the exact source version, units, value and effective period. Preserve discrepancy and reviewer outcome. Record versions of capability, input, model and prompt, resolved evidence IDs, decisions, timings and cost; avoid logging raw commercial documents and quote payloads.

Start any future model trial with one bounded read-only plan proposal, a token cap, a deadline and a server-side allowlist. Run validated steps through the current runtime and keep skipped, denied, timed-out and incomplete states. Separate network timeout from task deadline and implement cancellation. Disallow arbitrary SQL, writes and human-approval delegation. Restrict MCP to its current supported deployment profiles until delegated identity, legacy tool migration and security acceptance are proven.

## Event and performance architecture

Current scheduled debounce and SSE serve different purposes. Five minutes is an eligibility window between full scheduled runs. Source acquisition delay, scheduler wait and calculation duration still need measurement. Carry event time, source publication, receipt, projection and user-visible timestamps. Record revisions. Start with existing pending keys and a PostgreSQL transactional outbox only when failure recovery and re-evaluation requirements justify one. Use idempotent jobs keyed by event revision and snapshot, materiality filters, coalescing by dependency and version, deadline-aware priority and supersession. Recheck before persisting derived output. A late update can trigger replay under the relevant as-of cutoff.

Invalidate caches by snapshot and entitlement version. Prioritise urgent expiry/ETA cases separately from full re-optimisation. Bound scenario parallelism to preserve database and solver capacity, measure cold and warm solves, and test cancellation and retry before concurrency changes. Human reviews persist independently of jobs. Instrument receipt-to-detection, detection-to-first feasible scenario, time to quantitative recommendation, completion, CPU/solver time, model tokens/cost and human actions. Set desk SLOs after representative measurements segmented by workload and operating hours.

## Migration

Keep the experiment disconnected from runtime entry points. Promote evidence checks only after adopting canonical source IDs and valuation fields, proving row-level access and shadowing existing decisions. Maintain a deterministic fallback and scoped opt-in. Start event processing in shadow against current debounce, compare completeness, latency and allocator results, then move a narrow class after acceptance. An agent trial stays optional and removable without schema changes. Queue, worker and solver changes require their own ADRs and measurements.

## 18–36 month architecture and lifecycle policy

**Target.** A self-hostable modular application with PostgreSQL as transactional authority and source of point-in-time projections. Deterministic, volume-intensive workloads run separately from synchronous API work when warranted. Analytical exports and optional transports consume versioned contracts from this core. Customer installations can retain an air-gapped, extension-free baseline, including all deterministic desk and solver capabilities.

### Foundations to implement early

- **Stable entity ownership.** Retain existing network and ontology identities. The source registry owns external identifier bindings and provenance. Contract services own approved amendments, terms and rights. LNG and physical operations own cargo, terminal, inventory and status records. Portfolio services own books, exposures, approvals and commitments. Scenario projections and optimisation results own references to those versions and their assumptions. Preserve stable IDs through data migrations.
- **Temporal semantics.** Record source effective intervals, source publication and first platform availability separately. Standardise UTC instants, gas-day calendars and half-open delivery intervals. Store corrections append-only where point-in-time replay matters. Use knowledge and delivery cutoffs explicitly on snapshot reads. Qualify every unit conversion by basis, time and source version. Avoid rewriting legacy history when a source lacks availability evidence.
- **Event and workflow contracts.** The live scheduled-ingestion path now consumes a typed `opportunity.input.invalidated` v1 notice. It names source, run and class with the scheduler's notice time. This run-level message asserts neither an observation timestamp nor a revision-level market fact. Its identity is the source/run pair. A future broker can use a lossless encoding of that pair as its key, with type and version in the value. Future observation revision events should carry entity, dependency keys and availability separately. Add durable receipt, idempotent application, replay and quarantine before enabling a transport.
- **Public and analytical compatibility.** Generated schemas and golden fixtures should be part of contract tests. Publish OpenAPI changes additively and version breaking changes explicitly. In internal event contracts, decode a named version and reject unknown versions. Translate rolling upgrades with dual-version readers before switching a producer. Analytical manifests should specify entity keys, schema and snapshot version, UTC/time semantics, units, content digests and export entitlement. Keep the consuming research dataset builder and replay queries explicit in each interface proposal.
- **Migration baseline.** Inventory current uniqueness and foreign keys before changing physical storage. Keep canonical IDs outside the choice of partition layout. Use expand/backfill/checksum or count reconciliation/dual-read/switch/contract for shape changes. Verify as-of queries and views with old and new datasets. Delay irreversible cleanup until rollback is exercised. Prototype the tested invalidation wire format now with the existing CP-13 scheduler. This branch adds no DDL and implies no database migration test result.

### Technology decisions

| Technology | Decision | Lifecycle rationale, migration and operating cost |
| --- | --- | --- |
| PostgreSQL 16 baseline | **ADOPT_NOW** | Already the supported transactional engine, with existing Compose, Alembic, backups and access controls. The PostgreSQL License supports redistribution subject to notices. Keep API and UI independent of indexes and physical DDL. Budget ongoing schema, backup and disaster-recovery engineering once across deployments. |
| PostgreSQL declarative partitioning | **DESIGN_INTERFACE_NOW** | Design observed-time/availability query paths and retention now. Introduce range partitions first on a demonstrably growing append-heavy table with bounded time queries. Unique constraints on a partitioned parent must include partition keys, which can affect existing upserts and FK targets; preserve business identity in a suitable unpartitioned index/registry where needed. No extension licence or service. Rehearse migration and rollback with representative late revisions, pruning, locks, retention and restored DB performance. |
| TimescaleDB | **DEFER** | Its Apache edition and TSL Community features have distinct terms. Review exact version, binaries, notices and hosting/distribution rights before bundling either. Extension libraries, privileges, PG compatibility, backup/restore and customer upgrades impose ongoing support costs. Hypertable uniqueness and re-export can amplify migration cost. Prototype only if native partitioning and indexes fail explicit retention, compression or aggregate cost targets. |
| pgvector | **DESIGN_INTERFACE_NOW** | PostgreSQL-licensed extension, with an additional binary/version and indexing lifecycle. Use the contract-review or evidence-search consumer to define retrieval, snapshot, embedding model/version, provenance deletion and ACL tests. The default lexical/typed evidence path stays available. Build a disposable index from source references when evaluated, so removal or re-embedding does not alter authoritative records. A production extension install remains deferred until retrieval outperforms lexical search on entitled customer evidence. |
| DuckDB and Parquet | **DESIGN_INTERFACE_NOW** | Prefer interoperable Parquet files and manifests for reproducible research bundles. DuckDB is MIT-licensed and can be an embedded analyst-side reader. Vet readers, file-format versions, binaries and notices independently. Export entitlement and offline retention apply to copies. Version decimals, timestamp interpretation, nullability and schema evolution. Use customer-owned files, with a re-export rollback and no Cockpit/API dependency on a DuckDB database. |
| Kafka-compatible contracts | **DESIGN_INTERFACE_NOW** | Kafka is Apache-2.0 and self-hostable. A broker adds ACLs, credentials, monitoring, retention and upgrade/DR duties. Start with the typed scheduler contract and later durable PostgreSQL publication. Preserve keys and schema versions across transports. Use an opt-in adapter only for required independent consumers or when measured delivery/recovery outgrows database transport. Plan dual consumer checkpoint comparisons and a rollback to database transport. |
| Iceberg-compatible analytical storage | **DESIGN_INTERFACE_NOW** | Apache Iceberg provides a portable table format and stable field identifiers. Keep export schemas and manifests compatible with later adoption without shipping a catalog or requiring object storage. Catalog auth, object-store lifecycle, table commits, snapshots and maintenance add ongoing support and potentially managed-service fees. Consider an adapter for customer analytics that requires shared snapshot reads or table evolution; re-export plain Parquet for portability. |
| Temporal or comparable durable workflow infrastructure | **DESIGN_INTERFACE_NOW** | Map current job and research contracts to bounded retries, persisted deadline, input/version, individual attempts and replayable steps with idempotency and cancellation rules. Temporal's server is MIT-licensed, with its own persistence, worker versioning, auth, monitoring and upgrades. Keep serialized Nexus workflow state and business rules provider-neutral. Evaluate a self-hosted service only if PostgreSQL job orchestration proves operationally inadequate for long-running approvals, resumability or concurrency. |

No new prepackaged optional deployment profile is recommended for immediate support. A future **IMPLEMENT_OPTIONAL_NOW** proposal must include a tested version matrix (server, extensions, SDK/client), pinned reproducible local profile with offline binaries and notices, validated defaults and config, coexistence with the disabled profile, data migration validation, customer backup/restore, and an upgrade and rollback drill. These are integration acceptance criteria rather than claims that an optional service already works.

In the first year, prioritise stable entity and temporal interfaces, approved evidence, run-level notifications and migration rehearsal. Next, validate append-heavy observation partitioning and customer-controlled analytical exports, using representative retention, write amplification and replay tests. Activate service adapters only as a later measured deployment decision. Use case-specific AI opt-ins above those foundations, retaining the same API and desk workflow. This sequencing invests early in invariants and portable formats while keeping infrastructure installation reversible.
